## 10,000 张库存的快速基线

首次普通连接已在第 13–18 行枚举 10,000 个对象。随后对应主任务首次开启直播的批次是第 35–40 行：

1. `tx12` GetStorageIDs；
2. `tx13` 对槽 `65537` 请求 GetObjectHandles，得到不可用拒绝；
3. `tx14` 对槽 `131073` 请求 GetObjectHandles，返回 `photos=10000`。

该批次没有任何逐对象 GetObjectInfo、缩略图、高清预览或原图请求。第 41–42 行只是连接保活；截至检查点仍保持上述三个类别均为零。它支持“直播启动不再逐张确认库存”的协议结论，不能把初次连接及期间保活计成额外的启动基线工作。

本轮该清单批次首条命令到服务端枚举事件相隔约 **10 毫秒**，只反映模拟器到本机合成服务器的清单处理阶段。日志没有用户点击、项目落盘、UI 就绪回调与首帧绘制时间；因此不证明用户端总启动耗时，更不能承诺真实尼康相机或 10,000 张实体卡库存“秒开”。

启动后旧对象身份检查已变为有限闲时工作：例如第 69–107 行，每轮重新核对清单后仅有一个旧 handle 的 GetObjectInfo，依次为 `2、3、100、101、102`，间隔约 **3.03 秒**，没有把全部库存排入元数据队列。完整日志仅 **41 条** GetObjectInfo 针对初始旧对象；另外 **30 条**针对新 handle 4–10 的发现与接收核对。原库存没有任何原图请求，全部预览和原图请求目标均限定为新 handle 4–10。

第二次直播对应第 263–268 行的清单批次，返回 `photos=10004`，同样没有在接收 handle 8 前逐张读取旧库存。handle 4–7 在第二轮没有再次下载。

快速基线的保守边界仍存在：没有取得旧 handle 第一份身份前，无法凭 handle 判断它是否已被相机复用。协议日志不覆盖这项竞态；专门 host 回归采用第一份旧描述只建基线、之后观察到变化再接收的策略，不能据此声称任意 handle 复用都不会漏收。
