0.2.1-beta 根据手机实际画面修正与审核设计的偏差：红色下划线页签、白底居中导航、扁平主按钮与描边次操作、按比例展示的样片卡片，以及三步无线连接引导。详情、确认和结果等二级页面隐藏全局底栏。支持多个本地 NCP、旧版已选文件迁移、真实样片关联，以及可配置的 HTTPS 在线目录和校验下载。当前没有默认在线库地址，也未内置示意图中的演示预设或照片；在线库配置见 [目录格式说明](docs/preset-library.md)。

相册新增标准只读 PTP/IP 连接、JPEG 缩略图与分页、单张或多张流式下载、已下载照片离线查看及系统文件选择器另存。它尚未经过 Z6II 无线实测，不包含尼康专有配对认证，不能按 SnapBridge 支持范围承诺兼容。下载保存在应用的图片目录，卸载会清除此目录；需长期保留的照片可在详情中另存到所选位置。

本轮已在一加 PKG110 覆盖安装最终 0.2.1-beta，核对手机安装包与交付 APK 的 SHA-256 一致，并重捕本地列表、预设详情、在线库空态、相册及已下载空态、无线引导与相册横屏截图。同轮中间包还检查了 1.3 字号首页与引导滚动、深色首页与深色引导，具体范围和截图版本见 [界面实现记录](docs/ui-implementation-review.md)。检查后已恢复原字号、旋转及夜间模式设置。本轮没有连接相机，未验证相机确认与成功页、USB 导入、无线连接或照片下载；8515 项协议与持久化检查属于前轮 0.2.0-beta 的结果，本轮未重复运行，相关后端未修改。设计系统见 [DESIGN.md](DESIGN.md)。

## 0.2.1-beta 使用

安装 `dist/nikon-usb-0.2.1-beta-debug.apk`，可覆盖使用同一开发签名的旧版。首页“从手机添加 NCP”会将文件加入“我的预设”；打开预设可关联真实样片，或连接相机后确认导入到当前空槽。

“帮助与设置”提供在线预设库地址配置，格式见 [在线目录说明](docs/preset-library.md)。未配置服务时在线列表为空，本版没有内置精选预设或样片素材。

“相册 → 相机照片”包含无线连接引导，连接设置可手动指定地址；“已下载”可离线查看下载成功的 JPEG。该通道为待相机实测的标准 PTP/IP 实现，不承诺与 SnapBridge 同等兼容。本版构建及手机检查见 [0.2.1-beta 验证记录](dist/nikon-usb-0.2.1-beta-VALIDATION.txt)；前轮协议、持久化与签名核对保留在 [0.2.0-beta 验证记录](dist/nikon-usb-0.2.0-beta-VALIDATION.txt)。

## 既有技术验证与历史

安卓手机通过数据线连接 Nikon Z6II，不拔存储卡将兼容预设从手机导入相机。专用读取已取得实机报告，用户反馈 C1→C7 复制及后续 NCP 导入成功；未取得对应新版完整日志独立复核。0.1.8 引入的有限格式兼容适配保留已识别旧参数与原始曲线，新机参数由用户明确选择，不能称为尼康原生载入的等效实现。以下保留各实验版本的调查过程和当时验证边界。

## 产品方向与协议路线

产品目标是给旧机型提供类似尼康云创的预设管理与导入体验：手机承担预设获取、本地管理和机型适配，相机侧使用已经核实的接收或登记接口。SD 卡目录复制是已调查的一种通道；当前使用专用接口登记到相机自定义优化校准槽位。已在用户接受许可后取得官方 SDK，并核实 Z6II 专用接口说明；专用读取已通过实测，机内复制登记已获成功反馈。厂商写入仅在明确确认的空槽复制或 NCP 兼容预览入口可用。

[尼康云创的官方流程](https://onlinemanual.nikonimglib.com/z6III/en/picture_controls_42.html)是相机经 Wi-Fi 从服务端下载并在机内登记优化校准；[Zf 的官方固件增补说明](https://onlinemanual.nikonimglib.com/zf/en/add_nikon_imaging_cloud_388.html)也显示该机通过固件增加云创支持。这说明相机软件参与实现，不能把“官方未支持”直接当成第三方实现不可能的证据；同样不能据此断言任意机型只更新手机 App 就能增加接收能力。

对 Z6II，目前已实际读取机内优化校准，并收到用户的专用复制登记成功反馈。预设色彩能力与传输能力分别评估：可识别某个文件格式，不等于支持所有新机型配方参数；未来适配不能只改扩展名或宣称无损转换。当前可以管理原始 NCP、复制机内已有预设，并实验适配限定格式的旧 NCP；不提供云创配方下载或所有 NCP/NP2/NP3 的通用转换。

## 当前实现

0.1.8 新增“NCP 兼容试导入 · 机内空槽”。支持已核实的 638 字节、0100、36 字节预设记录加 578 字节自定义曲线子集，限 Standard/Neutral/Vivid/Portrait/Landscape 彩色基底、数字锐化/饱和度/色相、00/FF 旧元数据组合与曲线模式标志；未知记录、版本、Auto、单色或其它组合明确拒绝，不降级成猜测解析。名称、基底、已识别的旧数值和曲线进入适配数据；578 字节曲线原样复制，不交换曲线采样端序。

旧 NCP 不包含现代中等范围锐化和清晰度。导入前用户可选择这两项，UI 默认适配值分别为 1 和 0；还明确使用逐项锐化、quick=0，以及曲线模式对比度=0/亮度=0。这些是用户可审阅的兼容适配值，不是从无配对样本中推断的固件补全规则。预览列出这些值，最终确认后，后端从同一原始 NCP 和选项重新计算载荷，再复用新会话读取九槽、两次目标空槽检查、单次登记和精确读回。`ncpRegistrationVerified` 仅指该适配载荷登记并读回一致；`ncpImportVerified`、`conversionEquivalentToNative`、`photoEffectVerified` 保持 false，不能据登记成功宣称拍摄效果等效。

用户随后反馈 0.1.7 C1 复制到 C7 成功；这是一条人工实测反馈，本轮未收到该次写入的 JSON，尚不能独立复核其原始字节和全部阶段。下一次导入须重新读取空槽，不再使用此前 C7 为空的记录。用户原始 NCP 已在本机私有核验中通过转换：输出 614 字节、578 字节曲线逐字节保留；未把用户配方放入 APK 或测试。

0.1.7 新增“机内复制 · 空槽实测”。先完成只读读取，在 App 中明确选择来源自定义预设及目标空槽，确认后才会实际请求登记。它使用相机已返回的原始机内数据，不使用选定的 NCP 文件。后端在新会话中重新读取九个槽位，要求来源与确认快照完全一致、目标初次和临写前检查均为空，再发送一次专用登记请求并读回比较。占用、来源改变、读取失败或格式不支持时停止，不自动改槽、覆盖、重试、删除或回滚，也不选择当前优化校准。协议没有原子的“仅空槽才写”保证，最后检查与写入之间仍有竞态，因此操作期间不要在相机或其他应用中修改槽位。每次结果会替换报告，再次复制须先重新执行只读检查。

用户提供的 0.1.6 实机报告已确认：Z6II 固件 V1.62，标准优化校准返回 36 字节，C1–C6 已登记且各返回 614 字节，C7–C9 为 36 字节全零空槽；能力返回 28 字节，所有长度与 SHA-256 一致，读取流程完整，自有会话关闭获确认，未发送写入。此结果验证了专用读取通道，尚未验证专用登记。旧 NCP 不包含部分新机型参数，当前没有足够的原文件配对证据来确认补缺及曲线映射规则，因此不猜测这些参数，不把长度相近当成载荷兼容。

其后收到报告中所选的原始 NCP：638 字节、0100、SHA-256 与报告一致，记录边界及 578 字节曲线完整。其曲线与原 C1–C6 均不相同，用户确认此文件尚未载入相机，因此仍不是可供推导原生转换规则的配对样本。SDK 示例使用机内原始数据读写，没有找到接受 NCP 文件并补全新字段的公开入口。0.1.8 因此采用明确预览的兼容适配，不称为原生等效转换。用户原文件和逐槽比较结果仅保留在忽略提交的 `.research/device-inputs`，不嵌入 APK 或测试。

0.1.6 新增“读取机内优化校准 · 只读”，无需选择 NCP。它使用独立的只读操作白名单，查询标准优化校准能力和当前数据，再读取 C-1 至 C-9，按返回内容识别空槽。JSON 保留每项的原始数据、长度、SHA-256，以及失败时的操作、事务、参数和已读结果。此入口不能发送对象上传、优化校准写入、属性修改或删除请求；读取完成不等于预设导入完成。机内数据与 NCP 文件的编码不同，当前不把 NCP 内容直接作为机内载荷。

0.1.5 修复 0.1.4 新引入的 App 崩溃：USB 探测在记录查询上下文时，把原生 `long` 与可空 `Long` 混在条件表达式中，导致不含存储上下文的 `GetDeviceInfo` 等操作对空值自动拆箱，抛出 `Long.longValue()` 空指针。改为显式分支保留可空上下文；这是 App 实现问题，不能作为相机拒绝命令或不支持预设导入的证据。上传策略没有变化。

0.1.4 新增“目录诊断 · 只读”入口，无需选择 NCP。它对比标准 PTP 根目录查询和整张卡的 Association 目录对象查询；若目录格式筛选被明确拒绝，再执行有数量限制的全对象查询。报告记录查询参数、实际可见目录的名称/句柄/父对象/类型、原始错误码和不完整或截断状态。不读取照片内容，不创建目录，不发送上传指令，不会根据这份调查自动改变上传目标或放开写入。

0.1.3 新增“指定目录实测”：仅当用户手动选择这个入口时，Z6II 报告 `AccessCapability=0x0002`（只读，可删除）的卡也可进入受限实验。其余存储、空间、文件系统和操作能力检查保留；只能向 USB 列表中已经存在、位置与类型均通过检查的 `NIKON/CUSTOMPC` 请求创建新 NCP，不会创建目录。普通试传仍按只读标志停止。报告区分“请求实验”“选中只读卡”“路径已验证”“实际发送写请求”和相机返回的真实 PTP 错误；没有收到有效返回时保留 USB/协议阶段未确认的结果。

用户 0.1.2 实机截图已确认：只装 SD，存储 `0x00020001`，可移动 RAM `0x0004`，DCF `0x0003`，访问能力 `0x0002`，剩余空间充足。0.1.2 **在本地存储预检阶段停止，尚未向 `NIKON/CUSTOMPC` 发送写请求**。因此它并不能证明相机已经拒绝该特定目录。已知专用目录也不能反向证明 USB 标准 PTP 允许上传，仍需实测。

后续 0.1.3 实机截图显示，指定目录实测已通过存储选择，但在 `ExistingDirectoryCheck` 停止：当前 USB 对象视图未找到根目录下的 `NIKON`，最后成功操作为 `GetObjectInfo (0x1008)`，事务 4，存储 `0x00020001`。用户随后确认：已经导出预设，并能在相机“复制到照相机”列表中看到刚导出到 SD 卡的预设。因此卡上已有可供相机读取的预设，需进一步排查 USB 枚举/访问范围。截图本轮仍未发送对象写入请求，不能称为相机已拒绝上传；也没有记录该次根查询返回的对象名称，不能直接断言只显示了 DCIM。

用户提供的 0.1.5 JSON 报告补齐实测证据：Z `6_2`、固件 `V1.62`，存储 `0x00020001` 访问能力仍为 `0x0002`；根查询完整且仅返回 `DCIM`，全卡 Association 查询完整且仅返回 `DCIM` 与 `DCIM/100NZ6_2`。无截断、超时、选择器不匹配或协议错误，PTP 会话正常关闭，未发送任何对象写入。由此可以确认该次标准 PTP 目录视图未公开 `NIKON/CUSTOMPC`，当前 App 无法取得该路径的对象句柄；不能推广为所有 USB 模式都不可见，也不能说相机实际拒绝了该目录上传。未筛选格式的全卡对象查询本次没有执行。

同一台实机明确声明优化校准专用读取、写入、能力查询与扩展属性查询操作。这支持继续研究专用接口，不能证明 NCP 原始文件就是其载荷。当前不再以重复 SD 上传试验作为主要推进方式。用户已接受官方 SDK 许可，开发环境已取得 Z 系列 v2.1.0 SDK 及 Z6II 型号专用说明；SDK 文件与提取资料保留在忽略提交的本机研究目录，不随 APK 或源码发布。

0.1.2 修正：将标准 DCF 文件系统（`0x0003`）与 Generic Hierarchical（`0x0002`）一起作为目录候选；普通模式的只读、未知访问类型、非可移动卡和空间不足条件仍会拒绝上传。报告展示存储原始参数和每一项拒绝原因，并区分“存储条件检查失败”与真实 PTP 指令失败。

0.1.1 修正：查询存储前跳过低 16 位为零、没有逻辑介质的存储标识；逐个查询有效标识时，某个存储在 `GetStorageInfo` 返回 `0x2013 / StoreNotAvailable` 不再中止其它存储的检查。报告会保留不可用存储及错误发生的操作、事务和存储标识。这个错误可能与空卡槽或当前不可用的存储有关，不能仅凭错误码判定卡损坏，也不能据此确认上传是否受支持。若 `GetStorageIDs`、目录创建或文件上传本身返回错误，程序仍停止并报告具体步骤。

- 读取尼康 USB/PTP 设备信息、固件、相机报告的操作指令和存储卡状态。
- 通过独立只读入口读取机内标准优化校准与九个自定义槽位，保存原始返回值供后续格式适配。
- 手动选择来源与空槽后，实验复制机内已有预设；新会话复查来源与目标，写后读回逐字节核对。
- 对已支持的旧彩色曲线 NCP，预览并选择适配参数后，试登记到重新检查的空槽，保存转换元数据、读回差异和失败阶段。
- 用系统文件选择器导入 NCP，保存原始字节，并检查 `NCP\0` 签名、记录边界、`0100` 版本和终止标记。
- 实验性标准 PTP 上传，仅允许 Z6II：选择可写存储卡，在 `NIKON/CUSTOMPC` 中分配空闲的 `PICCON01.NCP` 到 `PICCON99.NCP`。
- “指定目录实测”入口可在上述受限条件下测试声明只读的卡，不把声明改成可写，也不假定目录具有特殊权限。
- 不请求覆盖或删除，避开列表中已有的文件名与对象句柄；对象创建位置、文件大小、读回字节、SHA-256 和目录可见性全部核对后，才报告文件传输通过。PTP 可能不公开全部卡上文件，不能据目录列表保证物理卡上没有隐藏同名文件。
- 部分失败保留诊断结果，说明相机上可能留下的目录/文件。不会自动删除相机上的对象。
- 报告可保存为 JSON。上述实验版本当时没有联网权限；0.2.0-beta 为在线预设与无线相册增加网络权限，仍不采集或保存相机序列号。

**文件传输通过不等于机内预设已安装。**传输后，需要断开数据线，在 Z6II 的“照片拍摄菜单 → 管理优化校准 → 载入/保存 → 复制到照相机”中载入到 C-1 至 C-9。双卡时使用“主插槽选择”指定的卡；应用报告实际写入的存储卡标识和描述，优先选择描述可确认为 SD 的卡。

## 0.1.x 实验界面的真机验证步骤（历史）

机内复制已获用户成功反馈，接下来验证 NCP 兼容试导入：

1. 覆盖安装 `dist/nikon-usb-0.1.8-lab-debug.apk`，确认首页显示 `0.1.8-lab`。
2. 打开相机并连接手机，点击第一张卡片中的“读取机内优化校准 · 只读”，允许 USB 访问；无需重新选择或导入 NCP。
3. 保存这份只读报告，选择要导入的 NCP，在“02 准备 NCP 文件”点击“NCP 兼容试导入 · 机内空槽”，选择当前空槽与适配参数，再生成预览。C7 已有用户复制的预设，不应再当空槽使用。
4. 核对预览的名称、来源参数、适配值及目标，确认后保持连接，不操作相机槽位或其他相机应用。App 复查并最多发送一次登记请求，读回完全一致才标记精确核对通过。若相机规范化数据导致差异，也会保留真实返回值，不把写请求获接受误称为逐字节核对通过。
5. 无论成功或失败，用“保存诊断报告”导出 JSON；若已尝试写入而结果未确认，先重新只读检查和查看相机菜单，避免盲目重试。
6. 读回通过后，断开数据线，在相机菜单检查目标槽是否出现、能否选择并拍摄使用。App 不自动切换当前预设，照片效果仍需人工确认。

机内复制入口仍保留，可用于对照专用写入。兼容适配尚未与同一 NCP 的相机原生载入逐项比较，拍摄效果需要人工确认。

原“目录诊断 · 只读”仍保留，可重新对比 USB 实际可见目录；它的结果不会自动改变上传目标或放开写入。

原文件试传流程仍保留：

1. 在安卓 8.0 或更新系统安装当前 APK。手机需要支持 USB 主机/OTG，使用可传输数据的线。
2. 打开 Z6II，用数据线连接手机；如果手机有 OTG 开关，先启用。关闭占用相机 USB 的其他应用。
3. 点击“检测相机 · 读取能力”，允许 USB 访问。检测本身不上传任何文件。
4. 选择有效 `.NCP` 文件。当前仅接受已研究的 `0100` 文件结构，其他格式或版本显示暂不支持。
5. 对本次已确认只读标志的 Z6II，可先断开手机，在相机“管理优化校准 → 载入/保存 → 复制到存储卡”中，将一个自定义优化校准导出到 SD 卡，以便相机建立 `NIKON/CUSTOMPC`。随后重新连接手机，选择 NCP，点击“指定目录实测”并阅读说明。若目录仍不在 USB 列表中，程序会停止，不会猜测或创建同名路径。普通可写卡也可选择原“试传到相机存储卡”入口。
6. 如果读回通过，断开数据线，在相机菜单载入预设。手动确认能否拍摄使用，这一步应用尚不能自动验证。
7. 如果被相机拒绝或出现连接错误，保存 JSON 报告。若报告显示写入已尝试，先检查相机卡上的目标文件，再决定是否重试；避免反复创建未验证文件。

不需要打开 USB 调试；手机是在作为相机的 USB 主机使用。

## 已知限制

- Z6II 报告支持 `SendObjectInfo/SendObject`，但公开资料尚未确认它允许向 `NIKON/CUSTOMPC` 写入普通 NCP 对象。相机可能拒绝目录创建或 NCP 文件格式；程序会准确报告该步骤的失败。
- 指定目录实验只使用标准 PTP 操作，目录存在不等于已证实可写。`SendObjectInfo` 被接受后就可能已登记新对象；后续失败时不能据此宣称没有写入，报告会保留文件名、句柄和实际完成阶段，不自动重试或清理。
- 已核实 Z6II 专用优化校准接口说明；只有用户明确确认机内复制或 NCP 兼容预览时，才可能发送专用登记请求。NCP 模式由后端重新解析并适配原文件，不直接上传 NCP 容器作为机内载荷。
- 结构检查不是相机兼容性认证。0.1.8 只支持明确限定的 NCP 子集，不进行 NP2/NP3 转换；新增参数为用户选择的适配值，不保证与尼康原生载入等效。
- 已收到 Z6II 只装 SD 卡时的探测、存储预检、指定目录检查、0.1.5 完整目录调查及 0.1.6 专用接口读取实机报告，并收到 0.1.7 C1→C7 复制成功反馈。开发环境没有连接相机；0.1.8 NCP 兼容登记、读回及拍摄效果仍需实机验证。编译成功和模拟协议测试不能代替真机测试。
- 当前只交付安卓技术验证；iOS 直连方案仍需另行验证。

## 构建

应用没有第三方运行时依赖，可以用 Android Studio 打开项目（AGP 8.9.2 / Gradle 8.11.1 / JDK 17 / Android SDK 35），或运行 `gradlew.bat :app:assembleDebug`。Wrapper 使用官方发布校验值。也提供直接调用官方 SDK 工具的 PowerShell 构建脚本，无需下载 Gradle：

```powershell
.\scripts\build-apk.ps1 -SdkRoot '你的 Android SDK 路径' -JdkRoot '你的 JDK 17 路径'
```

脚本要求已安装 `platforms;android-35` 和 `build-tools;35.0.0`。产物名称包含 `app/build.gradle` 中的版本号，当前为 `dist/nikon-usb-0.2.1-beta-debug.apk`，使用原有本地开发签名。增加 Java 类后先打包为 classes.jar 再交给 D8，避免 Windows 批处理命令长度限制。

纯 JVM 协议与模拟传输测试：

```powershell
.\tests\run.ps1 -JdkHome '你的 JDK 17 路径'
```

测试范围和纯 JVM 数据替身的边界见 [tests/PTP_CORE.md](tests/PTP_CORE.md)。

执行真实生产 `UsbProbe.probe()` 的独立 host 回归（Android USB 由最小模拟端点提供，不代表相机实测）：

```powershell
.\tests\run-probe.ps1 -JdkHome '你的 JDK 17 路径' -AndroidJar 'Android SDK 中的 android.jar 路径' -Reproduce014
```

`-Reproduce014` 仅在生成目录的源码副本中恢复旧表达式，以确认旧崩溃；生产源码不变。0.1.5 已通过 685 项真实探测流程 host 检查，并通过 ADB 覆盖安装到用户已授权的一加手机，核对版本 `0.1.5-lab` 和启动成功。其后收到的实机目录调查结果见上文；预设导入仍待验证。

0.1.6 构建与 APK v2/v3 签名校验通过，签名与已安装的 0.1.5 相同。纯 JVM 检查通过 3,984 项；最终生产探测 host 检查通过 1,138 项，其中原探测 685 项、专用读取 453 项。新的只读白名单、数据结构、分片、失败上下文与会话清理均有模拟覆盖。语义数据解析失败时保留原始返回值、停止后续读取并正常关闭自有会话；真正的容器、事务或响应不完整错误则关闭 USB，不继续发命令。其后用户已运行 0.1.6 并提供成功的实机读取报告，结果见上文。

0.1.7 已完成 Android 构建、v2/v3 签名及与 0.1.6 相同证书的校验。该版本本地普通探测 685 项、只读优化校准 453 项与空槽复制 788 项 host 检查通过；最终只修改复制流程的收尾取消处理后，单独复跑复制套件，未重复无关检查。此前 3,984 项纯 JVM 套件对应的生产代码未变化，当轮没有重跑。复制测试使用独立合成数据，不随测试分发用户的真实配方；验证范围包括来源变化和目标占用时零写、单次准确登记、读回差异、失败状态及取消清理。构建交付时电脑未检测到手机；后续用户提供了 C1→C7 复制成功反馈。

0.1.8 已完成 Android 构建、v2/v3 签名及与 0.1.7 相同证书的校验。本轮一次必要全套检查通过：纯 JVM 4,061 项（含新增 77 项 NCP 适配）、普通探测 685 项、只读优化校准 453 项、复制与 NCP 入口 1,004 项，共 6,203 项。用户原始文件在私有核验中转换为 614 字节且曲线完全保留，但不随测试分发，也不以该结果替代相机登记或效果验证。当前电脑未检测到手机，0.1.8 尚未安装。
