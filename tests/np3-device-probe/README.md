# NP3 native Android probe

This instrumentation is restricted to the disposable `emulator-5582` layer. Its run script verifies emulator hardware and enables airplane mode before launching the product. It never chooses a connected physical device.

```powershell
.\tests\np3-device-probe\build.ps1 -ExpectedVersion 79
# Install the frozen product APK on the owned emulator-5582 temporary layer first:
.\tests\np3-device-probe\run.ps1 -Theme light -ExpectedVersion 79 -ExpectedVersionName 0.13.11-beta -Scope monochrome-batch -ExpectedApkSha256 <frozen-sha256> -RunId monochrome-unique-run
```

The build reads four original Flexible/Creative samples from the fixed 142-recipe ZIP plus the exact Dreamy Mono/Peep and Scott's Ilford 400 LO originals from the fixed full ZIP into ignored local `.tooling/np3-native` assets. Archive and individual-file SHA values are checked. Only synthetic photographs are generated; no private image or NX reference image is included. The build compiles only probe source against Android 35 and uses the existing development signature. Product classes are accessed through reflection, so the probe cannot substitute a host rendering implementation. `build-audit.json` binds the probe APK, source and asset SHA values.

The default `renderer-only` scope covers BleachBypass/Quick sharp/Flexible v3 and all three monochrome recipes: exact factory/model identity, original recipe/library bytes, built-in synthetic template ownership and distinct recipes, transparent/translucent alpha, complete monochrome pixels, full 1800 × 1200 JPEG processing at 100%/37%/0%, exact same-encoder decoded reference pixels, sRGB/capture EXIF, unchanged source bytes/time, cancellation before and during spatial processing, and per-recipe array/JPEG pipeline timings. Scott uses its own standard-monochrome model identity; Dreamy retains its deep-tone identity. Partial strength intentionally retains source colour.

The optional `monochrome-batch` scope adds a separate actual `PhotoPresetBatch.startTracked` job for each recipe, using a new synthetic source shared between all three jobs so different preset identities must produce different paths and pixels. Each job must create one fresh monochrome output, preserve its exact original link and source bytes/time, match an independent complete `PhotoPresetRenderer` JPEG byte for byte, then reuse the same output without rewriting it. All batch JPEGs and their synthetic source are copied into the run evidence. The product batch path publishes originals and effects to MediaStore; read-only `publicationStatus` and provider-byte checks verify the effect rows committed and match the private output.

The same scope also exercises the photo editor's actual `startEdits` route: two fresh synthetic photos receive frozen independent drafts, Scott at 37% and Dreamy Peep at 100%. Both outputs must match their own independently rendered JPEG bytes and source links, preserve originals, commit original/effect MediaStore rows with matching content, and mark only the same draft exported. Repeating that same frozen set must reuse both output files without rewriting them. This is a native pipeline check, not a gesture-level UI test. The existing `full` scope separately exercises legacy Flexible batch/reuse/source links/MediaStore/UI.

The runner and instrumentation both bind the installed APK SHA, version code/name and dedicated emulator. Evidence uses a fresh RunId under `docs/validation/np3-native/<version>/monochrome-native/<RunId>/<scope>/<theme>`; existing records, including all 77/78 evidence, are never removed. Product installation is a separate explicit operator step. Unique synthetic photos and QA outputs live only in the disposable read-only AVD layer and local evidence. No result establishes Nikon equivalence, physical-phone speed, arbitrary JPEG fidelity or camera import compatibility. Historical reports retain their original scope; a prior lack of MediaStore assertions does not imply that its actual batch path did not publish.
